v0 by Vercel

Opened 2026-10-08. Public docs and public code only. A claim with no number on the page that states it is marked not public. Notes from 2026-10-01 are used only where a live page still says the same thing.

## 1. Product

v0 is a hosted agent that turns a prompt into a running web app, then deploys that app to Vercel. The docs overview says it builds landing pages, dashboards, stores, and full-stack apps, and that it can also update copy. It is not a section catalog you reorder inside one theme.

First input. Sign in at v0.app, start a chat or a project, and describe the app. The quickstart examples are a todo app, a SaaS landing page with a hero and pricing, an analytics dashboard, and a contact form that sends email. The same page also accepts a new project with no prompt yet. Other documented inputs, not required: a screenshot, mockup, or other upload; a Figma file; a GitHub repo; a ZIP; a Vercel project; voice (the microphone transcribes into the prompt, and you send it yourself). The text-prompting page opened today does not describe an enhance-prompt button. That 2026-10-01 note does not match this page.

A human does not have to approve a plan before the page exists. The quickstart path is prompt, then a generated app, then iteration. Plan Mode is an optional account instruction. When it is checked, v0 writes a plan and waits for approval before code changes. The API surfaces that pause as an agent action named `exit_plan_mode`. The caller resolves it with `plan-exit-response` and a status of approved, request-changes, or rejected. Complex-project advice on the text-prompting page (write a PRD, then say build the MVP) is a prompting habit, not a gate. You can also queue up to 10 prompts; they run in order without a stop between them.

Design system before copy is optional. New chats start from a Next.js app that uses shadcn/ui and Tailwind unless a design-system skill replaces that starter. Team owners on a paid plan can set one team skill as the default for new chats when nothing else is selected. A person can still pick another skill in the prompt toolbar. Import of a design system does pause: v0 builds a starter, and it does not save the skill until a person approves that starter.

Who reviews. The preview is the review. Design mode and the read-only code viewer are the other review surfaces. No visual-critic role is named. Publish is a second click, not the preview.

What must not be invented. On a design-system import, a component, prop, or token that cannot be verified from the sources should not be used. A rule against invented marketing copy is not public. The overview lists "update copy," and the marketing examples include generating copy. The FAQ sentence that screenshots and Figma become "pixel-perfect" apps is not a measured result. Not public.

Images. Upload from the prompt, drag and drop, or paste. Documented image types include PNG, JPEG, WebP, GIF, SVG, ICO, and AVIF. Chat attachment cap is 5 MB on Free and 20 MB on Premium, Plus, Business, and Enterprise. The page also tells you to use images at least 1024 px wide. Whether a generated photograph is a product feature is not public on the pages opened. The ChatGPT billing page says image generation, editing, and regeneration can still spend v0 credits. That is a billing line, not a procedure.

Publish gate. Preview deployments have their own URLs and do not change the production URL. Production is a separate Publish action in the chat header. First time: confirm the Vercel project name if needed, choose visibility, confirm the `vercel.app` domain or a custom domain, review commerce mode if Stripe or Shopify sandboxes are unclaimed, then Publish. Later: Publish, review, Publish Changes. With GitHub, Publish opens or reuses a pull request, merges it into the base branch, and still obeys branch protection. v0 does not push straight to `main`. The FAQ still says the second control is "Publish to Production." The deployments guide, same docs date, says Publish Changes. The guide is the procedure. A chat with no project gets one the first time that chat is published. Visibility choices depend on the team plan and deployment protection. That is access control, not a documented noindex switch.

The 2026-10-01 folders note is stale. `https://v0.app/docs/folders` now returns the product overview. The projects page does not say chats share a filesystem. It says one project shares deployment, hosting, domains, and environment variables. The sandbox page still says files, env vars, and processes do not cross chats. How a shared project and a per-chat sandbox fit together is not public.

The FAQ (body dated 17 March 2026, still served under a 2026-10-08 frontmatter) says a VS Code-style editor is built in. The code viewer page of the same docs date says the Code tab is read-only and that writing code is still a chat prompt. The code viewer page is the procedure for that tab.

## 2. Code libraries

Default stack the FAQ names: Next.js, React, TypeScript, Tailwind CSS, and shadcn/ui. The full-stack page says v0 defaults to Next.js because server actions and route handlers sit next to the UI, and that other frameworks are possible but less reliable. The sandbox starts a Next.js, Vite, or generic Node dev server. Prompt examples still say "Next.js 14." The public registry starter pins `next` 16.3.3, `react` 19, and `tailwindcss` 4. The Next version v0 writes into a new chat is not public. FAQ: generated AI features follow AI SDK 6. i18n, if you ask for it, is documented as a Next.js pattern with `next-intl`, not as a v0 library.

shadcn/ui is the default component system, described as source you own, not a versioned component package. The legacy design-systems page says v0 is trained on the default shadcn primitives and may mishandle customized ones. It can still emit other libraries if asked. Tailwind config and a global CSS file are accepted as generation context. Design mode, when the app uses Tailwind, offers Tailwind-compatible values. Class and token coverage depends on the project. Not a measured list.

How a section is stored. There is no public reorderable marketing-section record. In the running app, a route is a Next.js `page` file, shared chrome is a `layout`, and a section is whatever component source the page renders. Next.js (16.4.0 docs) treats `app/page`, `app/layout`, and colocated components as the file model. A folder is not a public URL until a `page` or `route` file is added. v0 does not publish its own map from a prompt noun ("hero") to a filename. That mapping is not public.

Two public ways to hand v0 a design system:

Legacy registry, still documented, marked legacy on the page. A registry is JSON that passes components, blocks, and tokens to the model. The spec is shadcn `registry-item.json`. Item types include `registry:base`, `registry:block`, `registry:component`, `registry:ui`, `registry:page`, `registry:file`, `registry:style`, `registry:theme`, `registry:hook`, `registry:lib`, and `registry:font`. Each file has a path, a type, and sometimes a target. `target` is required for `registry:page` and `registry:file`. Placeholders `@components/`, `@ui/`, `@lib/`, and `@hooks/` resolve through `components.json`. `cssVars` holds theme, light, and dark token names. The `tailwind` config block on an item is deprecated in favor of `cssVars.theme` for Tailwind v4.

The public template is `vercel/registry-starter` (opened on `main`). `registry.json` lists items. `pnpm registry:build` runs `shadcn@latest build` and writes `/r/{name}.json`. Open in v0 calls `v0.dev/chat/api/open` with that URL. The theme item targets `src/app/globals.css` plus `src/lib/utils.ts` and `src/hooks/use-mobile.ts`. The three blocks are `blank`, `dashboard`, and `store`. Each block's page file targets `src/app/page.tsx`, and a layout file targets `src/app/layout.tsx`. Named section components, as registry items rather than as a v0 theme, include `hero`, `promo`, `product-grid`, `brand-header`, `brand-sidebar`, `logo`, and `login`. UI primitives are single files under `src/components/ui/` with no target of their own. `components.json` in that repo sets style `new-york`, `rsc` true, `tsx` true, CSS variables on, empty Tailwind config path (v4), base color `gray`, and aliases `@/components`, `@/components/ui`, `@/lib`, `@/hooks`. Icon library name: `lucide`. The v0 legacy guide still points at `src/app/tokens.css`. That path is not the theme target in `registry.json` on `main`. The repo wins for the template. The guide wins for the product sentence that a registry is optional context.

`components.json` is an shadcn CLI file. It is optional if you paste components by hand. Fields that matter: `style`, `tailwind.css`, `tailwind.baseColor`, `tailwind.cssVariables`, `rsc`, `tsx`, aliases, and a `registries` map. The docs example includes a namespace `@v0` whose URL template is `https://v0.dev/chat/b/{name}`.

Design Systems 2.0 is the current product path. A design system is a skill in a team or personal scope, not a copy of the docs. It records where the source lives, which components, props, and tokens are safe, and how to wire a new app. Files: `SKILL.md`, `v0.json`, a starter directory, and an optional `logo.png` beside `SKILL.md` (upload cap 4 MB). `v0.json` version is `1`. `referenceWorkspace.sources` holds up to three read-only GitHub repos. `starter.source` is `skill-directory` (usual path `assets/starter`), `v0-default`, or `empty`. Figma frames, doc links, and attachments are import inputs. They are not kept as long-lived `v0.json` sources. Appearance colors in the skill frontmatter (`v0.kind: design-system`) recolor the skill in the composer. They do not change tokens in generated apps. The API loads a skill as `{ type: 'memory', scope, skillName }`. Other skill types on that page: `remote` (a public skill from skills.sh) and `project` (a skill in the connected repo). At most three skills per create or send. Mentioning a name in the prompt does not force the skill to load.

Sandbox. VM-backed chats run in Vercel Sandbox, a Firecracker microVM, not in the old browser preview and not on the production deployment. The v0 sandbox page: Node.js plus pnpm, npm, yarn, and bun; env vars from the connected Vercel project available to the app and to agent tools; filesystem kept for that chat; a pooled sandbox starts at 30 minutes, keep-alive adds 10 minutes when five or fewer remain, hard cap 24 hours from creation. Network policy default is `allow-all`. Team owners change it. The Vercel Sandbox product page names the JS package `@vercel/sandbox`, a Python SDK, and the `sandbox` CLI. Default image name on that page: `vercel/sandbox/universal`. v0's own chat lifetime numbers are the ones above, not the generic product page.

Closed. The agent's Read and Edit tool schema is not on the pages opened today. How the model chooses a section inside a free prompt is not public. The code viewer does not show a writable tree.

## 3. Mobile

No breakpoint, type size, tap size, or header rule is required by the docs. The only procedure is an example custom instruction: design for mobile screens first, then adapt. It applies only while that instruction is checked. The FAQ says you can build "mobile-responsive apps." That is not a measured layout. Not public.

Design mode does not run on mobile viewports, and it does not run on read-only chats or on older chat versions. An iOS app can prompt, preview, change env vars, connect GitHub, share, attach a database, and select MCP servers. Adding a new MCP preset is documented as desktop-only.

Next.js always emits a viewport meta of `width=device-width, initial-scale=1` when a route does not define its own. That is the framework default, not a v0 layout spec. The registry starter ships the hook file `use-mobile.ts` as part of the theme item. Its logic was not copied and is not a v0 requirement. Favicon, header, and hero procedures are not public. Hero appears in sample prompts and as a registry item name. A generated header and favicon are not public as required files.

## 4. SEO

Separate the v0 product from the Next.js library it usually emits. None of the following is a documented v0 feature, and none is a ranking promise.

Sitemap. Not public as something v0 writes or checks. Next.js will serve `app/sitemap.xml` or `app/sitemap.ts` if that file is in the app. v0 does not say it adds one.

Robots. Not public as a `robots.txt` or a meta robots tag that v0 always emits. Next.js can write `app/robots.ts` and a `metadata.robots` object (`index`, `follow`, and a `googleBot` block) if the app exports them. Deployment visibility, Deployment Protection, and Vercel Authentication decide who can open the URL. The deployments page does not say those switches write noindex.

Canonical. Not public in v0 docs. Next.js `metadata.alternates.canonical`, with `metadataBase`, is the library field. v0 does not say it sets one.

Title and description. Not public as a v0 form. Next.js `metadata.title` and `metadata.description` on a `layout` or `page` are the library fields. The full-stack page says React Server Components are for performance and SEO. That sentence is not a measured score.

Open Graph. Not public as a v0 field. Next.js file conventions are `opengraph-image` and `twitter-image`, and the metadata object has `openGraph`. v0 does not say it generates them. The registry starter depends on `@vercel/analytics` and `@vercel/speed-insights`. Those package names are in that repo. v0 does not say every chat installs them. The deployments page only links the Vercel dashboard for Web Analytics and Speed Insights.

JSON-LD. Not public in v0 docs. Next.js docs say to render a `script` of type `application/ld+json` yourself. No type list is required by v0. Not public.

Heading order. Not public. One h1 is not a documented check.

Internal links. Not public as a generator or a checker. A prompt can ask for a header, and the registry has a `brand-header` item. That is not an internal-link rule.

Page speed. Not public as a number. Speed Insights is a Vercel project screen linked from the deployments page. The "improved performance" line on the full-stack page is not a measurement.

Index controls. Chat privacy (who can open the chat) is separate from whether a deployed URL is indexed. Production visibility is documented. A robots index switch written by v0 is not public.

The marketing example "research keywords and optimize your SEO" is a prompt idea, not a procedure.

## 5. Dynamic behavior

The preview runtime is Node inside the sandbox. The production runtime is a Vercel deployment, a different machine, with its own env vars. The generated app is not static HTML.

Default app runtime is Next.js: React Server Components, server actions, and App Router route handlers. Client components are normal React when the file is a client component. With `components.json` `rsc` true, the shadcn CLI adds a client directive to client components. Vite and generic Node are the other dev servers the sandbox knows how to start.

Accounts. No v0-hosted user directory is documented. Supabase is documented as Postgres with auth. A prompt example names NextAuth. That is generated code, not a v0 account product.

Forms. A contact form is a quickstart example. The registry starter depends on `react-hook-form`, `zod`, and `@hookform/resolvers`, and it has a `form` UI item. Where a submission is stored is whatever that generation writes. A built-in form inbox is not public.

CMS. No v0 CMS. MCP presets include Contentful, Sanity, and Notion. Shopify is a separate integration for storefront and admin data. Commerce mode at publish is a claim step for an unclaimed Stripe test sandbox or Shopify development store, not a page builder.

Databases and other client behavior. Neon, Supabase, Upstash Redis, and Vercel Blob install from the project Integrations screen or from a chat suggestion. The databases page says SQL integrations can generate and execute SQL, including create, update, and drop. Client env names must start with `NEXT_PUBLIC_`. Marketplace and MCP tools run during generation. The generated app does not call those MCP tools. The MCP page says the generation itself cannot use MCP tools directly. Pair them with env vars if the app should call the service.

Other runtimes named in the product, not in the page: the in-chat agent (web search, browser screenshots, terminal, auto-fix of missing files, syntax, runtime errors, and imports), and a pre-installed `claude` process in the sandbox terminal. Installing other agents there is documented as unsupported. Enterprise leaves `claude` off until an admin opts in. Those are authoring tools. They are not the site runtime.

## 6. Already in SpiderCaster

The engine does not generate a Next app, and it should not start. These overlaps are the static pieces only.

A person already supplies the page before paint. `compose` reads real `copy/` files, then `apply_frame` keeps only section types the frame names, in that order, and does not invent one. Fourteen package frames live under `library/frames`. `welcome-scroll` is hero, about, features, gallery, faq, contact. That is the local stand-in for a design-system skill: one mold, `tokens_read` for theme knobs, no downloaded starter.

Sections are already records, not React files. One catalog part per section, plus a header and a footer. `tools apply` can append, replace, or paint a mold, and it refuses a path listed in `lock.txt`. The lock file is local. It is not v0's chat file lock.

Preview is not publish. Render defaults to a robots meta of noindex, nofollow. `library bind --live` is the human publish. There is no chat control that deploys.

Checks already cover the static SEO and mobile bars v0 never states: body text 18 px, chrome 16 px, contrast 4.5:1 (large text 3:1), tap 44 px, no sample or lorem, no hotlinked images, a relative canonical, one h1, WebSite JSON-LD and no aggregateRating, FAQ text visible when FAQPage is present, skip link, scroll-margin, sticky header, mobile drawer, no sideways overflow at 360, 390, and 412. `visit` measures at 390 and 1280 when Playwright is installed. Render already writes title, description, Open Graph title and description, a canonical to the page file, and a favicon link. The SEO seat's hands are `uniqueness` and `meta_basics`. `meta_basics` re-runs the checker and expects noindex.

## 7. Worth building

Do not import the registry, a skill from skills.sh, the registry-starter tree, shadcn, Tailwind, React, or the sandbox. Do not add a Publish button, Bash, browser use, or web search. Do not add a quote or review block because a registry item mentions a customer quote. Do not add Plan Mode as a chat. The copy files are the plan, and `apply_frame` already refuses a section the copy did not produce.

One static gap. The checker does not look for a sitemap or a `robots.txt`, and a search of `lib/` finds neither writer. Next.js only emits those files when the app contains them, and v0 does not check them. A stdlib writer may add `sitemap.xml` and `robots.txt` from pages already on disk, and only in the same step that clears noindex. URLs must be the pages compose already wrote. No extra URLs, no ranking copy. Until that human step, the existing noindex meta stays the index control.

Nothing else in the v0 stack fits a static, stdlib, real-copy build.
