Shopify Magic and Horizon themes

Notes dated 2026-10-01 are a head start. Where a page opened on 2026-10-08 disagrees, this report follows the live page. No vendor HTML, Liquid, or CSS is copied. File roles, setting ids, and short public identifiers only. Claims that were not on an opened page, or that a page states as a ranking effect without a measurement, are marked not public or as an unmeasured claim.

## 1. Product

Shopify Magic is no longer the name on the English theme-editor articles. On 2026-10-08 those articles say Sidekick writes the result. The older name still appears as the Magic icon's alt text, "Generate text." The English AI-tools page lists several generators. It does not publish one skill file. A skill manifest is not public.

What it builds, and the first input:

- A whole theme. In the Shopify app, or in the admin in a mobile browser: Online Store, Manage themes, describe the business under Design your store in seconds, Generate themes (up to 3), then Try theme. The theme is added under Draft themes. Desktop admin can no longer start that generation. Previously generated themes can still be previewed from a desktop browser. When the storefront language is English, new generation is only during the free trial or on Basic, Grow, or Advanced. The Starter plan cannot generate one; it is limited to the Spotlight theme. Plus is not in that eligibility sentence. Theme slots are a different limit: Starter is Spotlight only, Basic, Grow, and Advanced hold up to 20 themes, Plus up to 100. Certain policy-violating topics cannot be used. There is no token step before the generated theme. The description is the design.
- Text inside a theme that already exists. Edit theme, select a text element that shows the generate icon (the example is an image-banner heading), prompt for a headline, title, subtitle, or announcement, optionally with a tone. The prompt language is the output language. The text is applied to that field. The merchant may edit it, then Save. Fields without the icon cannot generate.
- A theme block inside a section that accepts theme blocks. Edit theme, open the template (home is the default), click the section, Add block, Generate, describe the block, Generate. Sidekick writes the code. Preview it, try any generated settings, then Keep, discard, or send a follow-up. Keep adds the block to the block picker for compatible sections and writes a self-contained Liquid file under blocks, so a later theme-store update can still be applied. Prompts must be at least five words and should name the content, the layout, and the settings that should stay editable. The help example says to stack the block on mobile. Vintage themes cannot generate blocks. Paid Theme Store themes must be purchased first; a trial cannot use the AI code generator. The feature is not on the Starter plan. The English page says the store must be on one of a listed set of plans, and that list did not render, so the English plan names beyond "not Starter" are not public from that open. Who may generate: store owner, organization owner, Administrator, Organization administrator, or a Store role with the Edit Code permission. Support will not troubleshoot the generated code.
- An image the merchant already has, in the file editor: replace the background with a color, or have Sidekick change the image from a text prompt. Tinker is a separate free mobile app for images, videos, and brand assets. How theme generation chooses a hero photo is not public.
- Sidekick, from the theme editor, can also be asked to change colors, fonts, and layout settings, including on an unpublished theme. The merchant must Save. It does not publish by itself.

There is no plan the human approves before the page exists. Theme generation produces up to three themes, then the human picks one with Try theme. Text and blocks are reviewed after they land in the editor. The caution on text generation says the merchant is responsible for accuracy, because generated text can invent product facts (the example is a wash guarantee that the product does not have). The block page says generated code can miss accessibility or performance practice, and the merchant must review and test it. The AI-tools page says review anything a tool creates before it is applied. No automated visual critic is named.

Publish is a later, separate action. Try theme and Save do not make the theme the live one. Only one theme can be published at a time. A visitor preview link expires after 2 days and needs no login. A merchant preview expires after 30 days and can open checkout. Store access starts in private mode: pages are hidden from visitors and search engines behind a password page. Public is an explicit access change. A theme bought from the Theme Store is licensed to that store. A trial theme cannot be code-edited.

A specific ban on fake reviews is not public. The block-prompt examples include a testimonial with a customer photo, a quote, a name, and a 5-star rating display. Shopify's copyright note says it does not support uploading images from the web or copyright infringement. That is not a reviews rule.

## 2. Code libraries

Horizon is Shopify's public flagship Liquid theme, repository Shopify/horizon, default branch main, language Liquid, theme_version 4.2.0 in config/settings_schema.json. The release-notes file on that branch is titled 4.2.0. The repo was pushed 2026-09-21. License SPDX is NOASSERTION. Contributions are not accepted. The README says main may contain unreleased Liquid. It also says Theme Store submissions must not be built from, derived from, or incorporating Horizon. The approved Theme Store base named on the requirements page is the Skeleton theme. Dawn remains the architecture docs' reference theme. Neither theme is a SpiderCaster mold.

Architecture, three kinds, from the versions page. Vintage (sectioned or not; no longer in the Theme Store). Online Store 2.0 (sections on every page, JSON templates, dynamic sources, app blocks and app embeds). Theme blocks, the latest kind, which includes the Horizon family and keeps the OS 2.0 features. A draft slot can hold a different architecture than the live theme. The theme-store version number is not the architecture kind. A blocks directory in the code editor is the merchant check for theme blocks.

A theme directory is assets, blocks, config, layout, locales, sections, snippets, and templates, with templates/customers and templates/metaobject as the only extra subdirectories the architecture page allows. Only layout/theme.liquid is required to upload. Horizon's public tree has layout/theme.liquid and layout/password.liquid. A templates/customers directory returned 404 on 2026-10-08, so legacy customer-account templates are not in that tree. Snippets are reusable Liquid and are invisible in the theme editor. Locale files hold merchant-editable strings. Assets hold CSS, JavaScript, and images. There is no public npm package, Tailwind build, or shadcn registry. The CSS system is the theme's own files. Measured asset names include base.css, overflow-list.css, and template-giftcard.css, plus one script file per behavior (header-drawer.js, header-menu.js, predictive-search.js, cart-drawer.js, section-renderer.js, section-hydration.js, and others). The 125-file assets directory was not fully listed. theme.liquid renders the snippets meta-tags, color-palette, theme-styles-variables, fonts, stylesheets, scripts, and skip-to-content-link. Those snippet names are the token and head roles. Their source was not copied.

How a section is stored. The section definition is a Liquid file in sections with one schema tag (name, settings, blocks, presets, and optional limit). The instance is JSON, not the Liquid file. A JSON template has an order array and a sections object. Each section entry has a type (the filename without the extension), settings, blocks, and usually a block_order. A block entry has a type and settings. Platform docs also allow a disabled flag so a section stays in the template but is not rendered. Section groups are JSON files in sections, rendered from the layout, so the merchant can reorder sections in the header and footer without editing the page template. A theme can hold up to 1,000 JSON templates. No template file is required until that page type must render.

Measured Horizon JSON, types and order only:

- templates/index.json order is a hero section, then a product-list section. The hero's block_order is a text block, then a button block. The hero settings include vertical_on_mobile. The product list has no block_order. Its blocks are static: _product-list-content and _product-card. Settings include carousel_on_mobile, mobile_columns, and mobile_card_size. Preset marketing sentences in those settings are not copied here.
- sections/header-group.json order is header-announcements, then header. The announcement block type is _announcement. The header's blocks, with no block_order, are _header-logo and _header-menu. The sticky setting id is enable_sticky_header and its value is always. Also measured: logo_position left, menu_position left, menu_row top.
- sections/footer-group.json order is footer, then footer-utilities. Footer block types in order are group, menu, menu. Utilities block types are footer-copyright, footer-policy-list, social-links. That is not the architecture doc's newsletter-then-quick-links example. The live file wins.

Other section filenames in the public sections directory, as roles only: _blocks, carousel, cart-drawer-section, collection-links, collection-list, custom-liquid, divider, featured-blog-posts, featured-product, featured-product-information, header, hero, layered-slideshow, logo, marquee, media-with-content, password, password-footer, predictive-search, predictive-search-empty, product-hotspots, product-information, product-list, product-recommendations, quick-order-list, search-header, search-results, section, section-rendering-product-card, slideshow, and the main-* page sections for 404, blog, blog post, cart, collection, collection list, and page. Template filenames: 404, article, blog, cart, collection, gift_card.liquid, index, list-collections, page, page.contact, password, product, search.

Blocks. Three sources. App blocks come from installed apps. Section blocks are defined inside one section. Theme blocks are files in blocks and can nest. One section accepts theme blocks or section blocks, not both. Nesting stops at eight levels, not counting the section. A template holds at most 25 sections and 1,250 blocks. Per-type caps are set by the theme. A required or static block can be customized or hidden, not reordered or deleted, and a static block does not count toward max_blocks. A restricted block appears only where it is listed. An illegal drag returns to the old position. Schema type @theme means other theme blocks. @app means app blocks. A named type restricts the child. Theme blocks cannot define local blocks in that schema. Sections can. Generated blocks are theme blocks. They are not sections. When Sidekick generates a block into a new section, Shopify wraps it in a platform section. A theme may ship its own sections/_blocks.liquid. Horizon does. The documented wrapper rules are: accept @theme and @app, define presets, emit the content_for blocks tag, and do not set templates, including inside disabled_on or enabled_on. The wrapper is not in the merchant Add section list and cannot be rendered with the section tag. The Horizon file was not opened, so whether that file meets every rule is not public from this pass.

Theme settings are global, separate from one section. They live in config/settings_schema.json (the editor groups) and config/settings_data.json (the values). Horizon's schema groups, as translation keys, are logo_and_favicon, colors, typography, page_layout, animations, badges, buttons, cart, drawers, icons, input_fields, popovers_and_modals, prices, product_cards, search, swatches, and variant_pickers. theme_info records the name Horizon and version 4.2.0. Values were not copied. Help describes two color systems. Color palettes, Horizon 4.0.0 and later: named brand colors for the whole theme. A section or block color can override one use or point at another palette color. Changing a palette color updates every use. Color schemes, most themes from before Horizon 4.0.0, including earlier free Shopify themes: a set such as background, text, and button, applied per section, up to 21 schemes. Whether every file in Horizon 4.2.0 uses palettes rather than schemes was not audited file by file. Help also documents, as theme settings, logo (max width 300 px, optional alt text), favicon (recommended 32 by 32 px, under Logo or Favicon depending on the theme version), typography (headings and body, font size scale 100% to 150% in 5% steps), layout (page width 1000 to 1600 px, default 1600, up to 100 px between template sections), animations (reveal sections on scroll, on by default; hover is vertical lift or 3D lift), social accounts, search suggestions, currency codes, and cart type drawer, page, or popup notification. Colors and fonts do not carry over when the merchant switches themes. A theme style is a designer preset of those settings. Custom CSS in theme settings applies to the store except checkout. That box is not a library to import.

Theme Check is the Liquid and JSON linter, also run from the Shopify CLI as shopify theme check. shopify theme dev makes a hidden development theme that is not the published theme. shopify theme publish is a store publish and is out of scope here. A July 2026 developer preview adds Liquid block and partial tags so a page can be composed in a Liquid template, beside JSON templates. It is not how Horizon's index is stored. The public index is still JSON.

The merchant editor groups the page into Header, Template, and Footer. The home template loads by default. Merchants add, reorder, duplicate, copy, paste, hide, delete, and rename sections and blocks, then Save. Incompatible moves snap back. Dynamic sources connect a setting to a metafield or metaobject on OS 2.0 and theme-block themes. The editor sidebar is the tree of the current template. Above 1600 px, customization options sit on the right. The sections article says that below 1600 px they sit on the left. An earlier features-overview note said the narrow layout slides settings up from the bottom. That features page was not re-opened on 2026-10-08, so the narrow-layout detail is not restated as current.

## 3. Mobile

Theme generation runs only in the Shopify app or a mobile browser. The theme editor itself has mobile steps: add, reorder, hide, and remove sections from the app, then Save. Block generation tells the merchant to preview desktop and mobile. The documented prompt line is "Stack on mobile." Horizon's measured settings for that idea are vertical_on_mobile on the hero, and carousel_on_mobile, mobile_columns, and mobile_card_size on the product list. Button blocks also have width_mobile and custom_width_mobile. A numeric breakpoint for those settings is not public from the JSON keys. header-drawer.js is the client file for the header drawer. Its breakpoint was not read.

Theme Store listing screenshots must include one mobile home-page image at 750 by 1334 px and one desktop image at 1000 by 1248 px or 2000 by 2496 px. That is a listing asset, not a generated layout.

Accessibility best practices, which Theme Store themes are pointed at: do not lock zoom with maximum-scale or user-scalable=no. Pinch zoom stays available. Primary touch targets are at least 44 by 44 px, including main-menu links, form submit, search, add to cart, the cart button, the hamburger-menu button, modal close, and variant controls. A skip link is required and must show when focused. Headings go in sequence, with one h1 for the page topic. Navigation is a nav element, not role=menu. Drawers and modals use dialog, move focus inside, trap keyboard focus, and close on Esc. The same page's contrast floors are 4.5:1 for text under 24 px regular or 18.5 px bold, and 3:1 for larger text and for icons. Those are authoring requirements, not a measured score of the Horizon demo store. A Lighthouse numeric floor was not in the requirements excerpt opened, so the minimum score is not public here.

The performance doc on content parity says mobile and desktop must carry the same core content, because Google uses the mobile version for indexing. It tells themes not to drop sections on small screens, not to use a separate mobile URL, and not to hide important text with display:none. The same doc says content hidden in tabs is given less weight. That weight claim is the page's account of Google, not a measurement made here. Responsive images should be the same picture at several widths via srcset and sizes. The hero performance doc says the largest first paint must be an img in the HTML, not a CSS background, so the preload scanner can see it. The first hero is eager and may use fetchpriority=high. Later copies of that section may be lazy. It names Horizon's hero section as the theme that covers the section with that image and stacks the text above it. The hero Liquid file was not opened. Release 4.2.0 sets the HTML dir attribute from the shopper's locale and uses logical start/end alignment so right-to-left pages mirror. It also says smaller product-card images are served in two-column mobile collection and search grids. The pixel sizes of those images were not copied.

Typography scale and page width are theme settings, not a phone layout. Page width never goes below 1000 px in that slider, so it is a desktop cap. Phone layout is the section settings and the theme CSS, which were not copied.

## 4. SEO

Documented features, separate from ranking sentences.

Sitemap. Shopify generates sitemap.xml at the domain root and updates it when products, collections, pages, images, or blog posts change. It links to separate sitemaps for products, collections, blogs, and webpages. The merchant submits sitemap.xml in Google Search Console. A sitemap reader cannot fetch it while the store is in private mode. Markets can add hreflang annotations. The sitemap article still names the plans Basic, Shopify, Advanced Shopify, and Shopify Plus. The themes article opened the same day says Basic, Grow, and Advanced. Both wordings are left as written. Which name is current in billing is not public from these two pages.

Robots. A default robots.txt is generated. The merchant can add templates/robots.txt.liquid to allow or disallow URLs, add a crawl-delay, add sitemap URLs, or name crawlers. Help calls that edit unsupported and says a bad file can drop traffic. Default rules named on the page: Allow /, Disallow /admin, Disallow /cart/, Disallow /checkout and /checkouts/, Disallow /account and /orders, Disallow filtered and sorted collection URLs. A theme that still outputs older groups can also disallow /search and /policies/. Crawling and indexing are described as different. robots.txt does not stop product data that Shopify Catalog sends to agentic storefronts the merchant has turned on. Those rules are advisory.

Canonical. Auto-generated. The theme metadata guide puts a canonical link in the head from the canonical_url object. Market versions are self-referencing and connected with hreflang, which is on by default and can be turned off under Online Store, Preferences, Social sharing image and SEO. Horizon's meta-tags snippet includes rel=canonical. The href pattern was not copied.

Title and description. Themes emit a title that includes the store name, from page_title. A meta description is emitted when page_description is set. Homepage title and description are edited under Online Store, Preferences, in Social sharing image and SEO. Products, collections, pages, and blog posts use the search-engine listing on that resource. The keywords page says the title field accepts 70 characters and advises 60 so results are not shortened, and it recommends about 160 characters for the description. The SEO overview table says title under 60 and description under 160. Both are editing advice. The keywords page also says each page should have at least 250 words and informational pages at least 500. That is the help page's advice, not a measured ranking result. Blank titles fall back to the shop name plus the content title. Google may rewrite the title or description that Shopify outputs. That limit is stated on the page.

Open Graph. If a theme omits og:image, Shopify can emit og:image, og:image:secure_url, og:image:width, and og:image:height from page_image. Featured images are used for products, collections, and blog posts. Other pages use the social sharing image. Priority on the social-image page: an image hard-coded in the theme, then a theme-settings image, then the Preferences image. Horizon's meta-tags snippet names og:title, og:description, og:image, og:image:width, og:image:height, og:image:secure_url, og:site_name, og:type, og:url, og:price:amount, and og:price:currency, plus twitter:card, twitter:title, twitter:description, and twitter:site. It also names description, viewport, and theme-color. The markup was not copied.

JSON-LD. The Liquid filter structured_data accepts a product or an article. A product with no variants is schema.org Product. A product with variants is ProductGroup. An article is Article. The documented product output includes brand, offers, price, and availability. The sitemap help page says current Shopify themes include microdata for prices, availability, and reviews, and that this can show as rich snippets. That is a documented feature. It is not a ranking measurement, and this pass did not find a JSON-LD script inside Horizon's meta-tags snippet. A full-tree search for structured_data was not finished, so which Horizon file emits Product or review markup is not public here. FAQPage, BreadcrumbList, and Organization as Horizon outputs are not public from the files opened. WebSite as a Horizon type is not public here.

Headings. SEO overview says H1 for the page title and H2 and H3 for subsections, and that themes made by Shopify are built with that in mind. The accessibility page requires sequential headings and a single h1. The keywords page says the resource title becomes the H1. An audit of Horizon's heading tags was not done.

Internal links. Help tells the merchant to use descriptive link text, to put every page in a menu, and to nest menus from homepage to collections to products. The content-parity doc says the mobile menu must carry the same links as the desktop menu. Whether Horizon's header-drawer does that was not verified by reading the script.

Page speed. Theme Check includes performance checks. The hero doc is about discovery of the LCP image, not a score. The Theme Store requires a Lighthouse performance and accessibility check against a benchmark shop. The numeric bar was not on the excerpt opened, so it is not public here. SSL is on by default. The SEO overview says that boosts security and rankings. The rankings half is the page's claim, not a measurement.

Index controls. Private mode hides the online store from visitors and from search engines and shows a password page. New stores start private. Public is a separate control. A sitemap cannot be read while private. Password-page sections in the editor are a password header, the page body, and a password footer. Horizon ships password and password-footer sections and templates/password.json. Help's default email-signup banner on that page was not confirmed in the Horizon JSON. There is no per-page noindex switch on the pages opened. robots.txt can disallow a path, and the page warns that disallow is not the same as keeping a URL out of the index.

## 5. Dynamic behavior

The storefront runtime for Horizon is server-rendered Liquid on Shopify, plus small browser scripts in assets. The README says business logic, translations, and money formatting stay on the server, and that async refresh of part of a page is a spare progressive enhancement. It is not a React app. Hydrogen is a separate stack and is not this theme. Client file roles measured by name: header drawer and menu, predictive search, cart drawer, section renderer, and section hydration. What those scripts do beyond the filename was not read.

The commerce CMS is the admin, not the theme: products, collections, pages, blogs, menus, metafields, and metaobjects. Dynamic sources bind a section or block setting to that data on OS 2.0 and theme-block themes. Alternate JSON templates can be assigned to a resource. Metaobject templates can publish entries as pages. Forms present as files or blocks: contact-form, email-signup, the password form, product add-to-cart, and a cart note. Cart UI is a theme setting: drawer, page, or popup. Predictive search is an OS 2.0 and theme-block feature and can be turned off under search behavior. Customer accounts are not a templates/customers directory in the public Horizon tree. The robots page still disallows /account and /orders. How the current account UI is hosted is not public from that 404. App embeds and app blocks inject third-party UI. Checkout is not themed by the online-store theme, and custom CSS does not apply there.

A July 2026 developer preview can refresh a named server-rendered region without a client framework. That preview is not Horizon's current template model.

## 6. Already in SpiderCaster

The engine does not generate a theme from a sentence, and it does not write copy. compose reads real copy files, may reorder only section types the copy already produced, paints one mold, and inserts one catalog part per section plus a renderer-owned header and footer. That split matches Header, Template, and Footer without a new section type. Output is structure.json, site.json, and report.json. The build stays noindex until a human runs library bind --live. Save is not publish. One mold is refused on a second live site. warmth-authority is already live and must not be bound again.

The checker already enforces body text 18 px, chrome 16 px, contrast 4.5:1 (large text 3:1), 44 px taps, no sample or lorem, no hotlinked images, a relative canonical, one h1, WebSite JSON-LD with no aggregateRating, FAQPage only when the FAQ text is visible, a skip link, scroll-margin, a sticky header, a mobile drawer, and no sideways overflow at 360, 390, and 412. visit measures at 390 and 1280 when Playwright is installed. The viewport meta sets device width and does not lock zoom. The hero is an img, not a CSS background, with sizes and fetchpriority=high, and width and height when the copy supplies them. og:title, og:description, og:type, and a local og:image are emitted from the same title, description, and hero. FAQ JSON-LD is a second script and only from real question and answer strings. The SEO seat can run uniqueness and meta_basics, and seat_gate refuses any other hand. Molds already store one palette, type, and nav, separate from section copy. The header stays sticky rather than hiding until scroll-up, which matches Horizon's always value, not Dawn's on-scroll-up. Favicon is a local SVG. None of this imports Liquid.

## 7. Worth building

Only static HTML, the standard library, real copy, and noindex until a human publishes. Reimplement. Do not import Horizon, Dawn, or Skeleton. Do not add React, Tailwind, a chat button, a Liquid emitter, app blocks, a cart, accounts, predictive search, or a stock image library. Do not generate text to satisfy the 250-word advice. Do not add a testimonial, a star rating, or Product JSON-LD. Shopify's prompt example includes a 5-star display, and a ban is not public there. SpiderCaster still does not invent reviews.

- A heading-sequence check. Fail a skipped level, and keep the existing one-h1 rule. Shopify's accessibility page requires sequential headings. This is a checker, not a ranking promise.
- Named color roles on the mold the renderer already paints, such as background, text, and accent, so one edit updates every section. Check them at the existing contrast floors. Horizon palettes are that idea. The current molds store a single accent hex. Do not copy Horizon's settings_schema or any CSS variable block.
- A sitemap.xml and a robots.txt written only when a human binds the site live, listing pages that exist, with no cart or account rules to copy. While the build is noindex, do not emit an indexable sitemap. Private mode is the Shopify analogue. The human gate stays library bind --live.
- Hide a section without deleting its copy, as a disabled flag in the existing structure file. Shopify's JSON template can do this. The frame must still not invent a section type the copy does not have.

Not worth building: a srcset pipeline. The hero already sets sizes and fetchpriority, and width and height when known. The standard library does not resize images, and a remote image CDN is out of scope. Twitter card tags would only repeat the Open Graph fields already written. A 25-section cap, an 8-level block tree, and a custom-CSS box do not fit a static catalog of sections.
